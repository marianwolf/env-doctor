# Plan: `.env` und `.env.example` für env-doctor anlegen

## Kontext
`env-doctor` (abhangigkeitsfreies ESM-CLI-Paket, GPL-3.0-only) validiert eine `.env`-Datei gegen eine `.env.example`-Vorlage inklusive Typ-Prüfung. Der Parser in `src/parser.js:20-21` liest Typ-Annotationen im Format `# type: <type>` aus (unterstützt: `number`, `boolean`, `url`, `string` – Default `string`).

Im Repo gab es bislang weder `.env.example` noch `.env`, also läuft `npm test` (→ `node bin/cli.js` → `diagnose('.env.example', '.env')`) nicht sinnvoll.

## Zwei Dateien anlegen

### 1. `.env.example` (Vorlage, wird committed)
```ini
# env-doctor — Vorlage für Umgebungsvariablen
# Typ-Annotationen im Format "# type: <type>" werden vom Parser ausgewertet
# Supported types: number, boolean, url, string

PORT=3000 # type: number
NODE_ENV=development # type: string
DATABASE_URL=postgres://localhost:5432/envdoctor # type: url
DEBUG=false # type: boolean
API_KEY= # type: string
```

### 2. `.env` (reale Werte, wird NICHT committed)
```ini
PORT=3000
NODE_ENV=development
DATABASE_URL=postgres://localhost:5432/envdoctor
DEBUG=false
API_KEY=change-me
```

## Warum dieser Inhalt
- Alle Keys aus `.env.example` sind in `.env` vorhanden und typen-valid → `diagnose()` gibt `valid: true`, die CLI exitet mit Code 0.
- `DATABASE_URL` enthält kein `#`, damit der `#`-Split in `src/parser.js:20` den Typ-Kommentar korrekt trennt.
- `API_KEY` in `.env` hat einen Platzhalter-Wert (kein echtes Geheimnis), in `.env.example` ist er leer – demonstriert den "Fehlt"-Fall für Neulinge.

## Ausführung
1. `.env.example` mit obigem Inhalt anlegen (committed).
2. `.env` mit obigem Inhalt anlegen (lokal, nicht committen).
3. `.env` in `.gitignore` eintragen (→ gehört zum größeren Publishing-Plan, hier als Hinweis).
4. Validierung: `npm test` → erwartet Ausgabe `✅ Alle Umgebungsvariablen sind vollständig und gültig!` mit Exit-Code 0.
